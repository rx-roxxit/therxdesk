## The RX Desk overrides

The RX Desk is a fork of TryPost. Everything in `AGENTS.md` and `.ai/rules` applies, except where this section says otherwise. When the two disagree, this section wins.

### New copy is English only (owner decision November 2026)

This overrides the 16-locale rules in `AGENTS.md` ("Writing in-app copy", "Translated copy must fit its UI slot", "Emails"), but only for copy The RX Desk adds:

- Every new user-facing string (UI, errors, toasts, emails) is written in English only, in its own file, `lang/<locale>/rxdesk.php`. No RX Desk key goes into an upstream lang file.
- The file exists in all 16 locale folders with the same keys, and every locale holds the English text. `LocalizationParityTest` therefore stays green with no test change, the frontend never shows a missing key, and upstream merges never conflict, because upstream never touches `rxdesk.php`.
- Never translate these strings, and never add RX Desk keys to `tests/fixtures/single-line-copy.php`.
- Upstream strings stay as upstream ships them.
- Everything else about copy still applies: go through `__()` / `$t`, never write a literal, and build emails in Maizzle.

### Running commands (Docker on the VPS)

Nothing is installed on the host: PHP, Composer and Node live in the dev image, and every command runs in a one-off container as `app` (UID 1001, the host user `rxdev`). This overrides the Herd section of `AGENTS.md`, which does not apply here.

```sh
R="docker compose run --rm -T -u app app"

$R php artisan test --compact tests/Feature/Auth/RegistrationTest.php   # one file (or --filter=name)
$R php artisan test --compact --parallel --processes=4                  # full suite (Unit + Feature)
$R npm run build                                                        # Vite build
$R vendor/bin/pint --dirty --format agent                               # format PHP
$R php artisan make:test --pest SomeFeatureTest                         # any artisan / composer / npm command
```

- `run` starts only pgsql and redis and skips the entrypoint's bootstrap, so nothing writes into the checkout as root. Never run these through `docker compose exec app` or without `-u app`: files made as root (a `make:` class, `lang/php_*.json`, Wayfinder output) cannot be edited from the host and break the next `app` run.
- `compose.override.yaml` binds every dev port to 127.0.0.1 (Docker-published ports skip ufw) and sets UID/GID 1001. Keep it that way.
- Tests use the `trypost_test` database (`phpunit.xml`, `.env.testing`) in the dev `pgsql` container of this compose project. The dev stack never shares a container, volume or database with production, and tests are never run against the production compose file.
- `docker compose up -d` starts the full dev app (web on 127.0.0.1:8000, reach it with `ssh -L 8000:127.0.0.1:8000`). Upstream's container runs as root, so after `docker compose stop app` hand the generated files back before the next `app` command:
  `docker compose run --rm --no-deps app chown -R 1001:1001 lang resources/js public storage bootstrap/cache vendor node_modules .env`
- Baseline (November 2026): the full suite takes about 13 minutes and passes except `BillingControllerTest` › "an amount discount is formatted in the user's language". Upstream's Alpine image ships English ICU data only (no `icu-data-full`), so `pt-BR` currency formatting falls back to `$18.00`. Billing is off when self-hosted; do not chase this failure.
- After `docker compose down -v` (volumes wiped): `docker compose run --rm --no-deps app chown 1001:1001 vendor node_modules`, then `$R composer install` and `$R npm ci`.

### Signup (Signup codes, not open registration)

- Self-hosted `/register` opens without an Invite (`EnsureRegistrationEnabled` no longer 404s). A signup without an Invite needs a Signup code (`SignupCode::isRequiredFor()`): `RegisterRequest` checks it, and `CreateOwnerWithSignupCode` locks the code row and consumes it in the same transaction as `CreateUser`. - The System admin manages codes with `$R php artisan rxdesk:code create --note="..."`, `rxdesk:code list` and `rxdesk:code revoke <code>`.

### Video policy (what happens to a post's videos after it publishes)

- The Owner picks it on Preferences (`accounts.video_policy`: `keep` default, `delete`, `backup`; `PATCH app.settings.video-policy.update`, Owner only through `AccountPolicy::update`). The request accepts `VideoPolicy::selectable()`; `backup` joins it only while the Owner has a working Drive connection (`VideoPolicy::selectable(DriveConnection)`).
- `ScheduleVideoPolicy` (listener on `PostStatusChanged`) queues `ApplyVideoPolicy` one hour after a post moves into `published`; nothing else starts it. The job reads the policy when it runs, and `DeletePostVideos` re-reads the post under its lock and acts only while it is still published, so failed, retrying, pending and pending-review posts keep their files for `posts:retry`.
- **Google Drive for Backup** (Preferences, Owner only; `DriveBackupController`): a full-page offline sign-in on the existing Google media client (`GoogleMediaOAuth::authorizeOfflineUrl()`: `drive.file` only, `access_type=offline`, `prompt=consent`, never `include_granted_scopes`). The refresh token lives encrypted in `media_source_connections` under `Source::GoogleDriveBackup`, one row for the Owner, apart from the composer picker's sign-in (which is never stored). `Account::driveConnection()` reads it (`none` / `connected` / `needs_reconnect`, shared as the `driveConnection` Preferences prop); disconnecting (behind a plain confirmation on Preferences that says so) returns a Backup policy to Keep. A refused Video policy save restores the previous choice and toasts. When Google rejects the token, call `MarkDriveNeedsReconnect::execute($account)`: Preferences then asks to reconnect and Backup is refused until the Owner signs in again.
- **Setup:** the backup sign-in has its own redirect URI, so register it on the same Google OAuth client beside the picker's: `<APP_URL>/settings/preferences/drive/callback` (env `GOOGLE_MEDIA_BACKUP_REDIRECT`, in `.env.example` and `docker/.env.docker.example`). Client id and secret are the existing `GOOGLE_MEDIA_CLIENT_ID` / `GOOGLE_MEDIA_CLIENT_SECRET`. Google API hosts stay in `config/trypost.php` (`media_sources.google_oauth`, `google_drive`).
- **Backup** (`BackupPostVideos`, from `ApplyVideoPolicy`): each video goes to the Owner's Drive under `The RX Desk/<workspace>/<year-month>/<date>_<network>-<handle>_<post id>.<ext>` (dates in the Owner's zone) through `GoogleDriveBackup` (Drive v3 resumable upload, streamed from storage in `GOOGLE_DRIVE_BACKUP_CHUNK_BYTES` chunks, a multiple of 256 KiB; hosts `google_drive.api` / `upload_api`; an expired access token is refreshed with the stored refresh token). Posts created together (`post_group_id`, `Post::groupPostIds()`) upload each file once: a video's source is `meta.copied_from` (or its own id), any published post of the group may upload it under the file's cache lock (`video-backup:<group>:<source media>`), and the lock holder re-checks for a `backed_up` record with the same `source_media_id` first, so the group gets one Drive copy and every other post reuses it. A post whose file's lock is held by another run looks again every `ApplyVideoPolicy::WAIT_SECONDS` in a fresh job carrying the tries already used (waiting never uses a try up). A post whose job already ran under Keep keeps its file, even when a later post of its group backs the file up. A video leaves the server only through `DeletePostVideos::afterBackup()`, after Google confirmed the upload; a failed upload throws, keeps the file, releases the lock and is retried on the job's backoff (`tries` 6, about an hour).
- **Long uploads:** `ApplyVideoPolicy` runs on the `video-policy` queue. With Redis it uses its own connection (`config/queue.php` `video-policy`, `retry_after` 11400 s) and Horizon supervisor (`config/horizon.php` `video-policy`, timeout 10800 s, in every environment block); the job's `$timeout` is `TIMEOUT_SECONDS` (10500 s) and the upload lock lasts `BackupPostVideos::UPLOAD_LOCK_SECONDS` (job timeout + 300 s). Keep job timeout < supervisor timeout < `retry_after`, and the lock above the job timeout (`VideoBackupPipelineTest` checks it). Without Redis (sync, database) it stays on the default connection. A retry restarts the upload from its first byte (Drive sessions are not resumed across tries).
- **Backup failure** (`ApplyVideoPolicy`, `BackupPostVideos::fail()`): after the last try (or at once when Google rejects the Drive token, `invalid_grant` → `GoogleTokenRejected` → `MarkDriveNeedsReconnect` + `DriveBackupUnavailable`) the video's record becomes `backup_failed` (`attempts`, `last_error`, never shown in the payload), the file stays on the server, and the Owner gets one English `VideoBackupFailed` email (Maizzle `video-backup-failed`, copy in `rxdesk.php`). Each post of a group tries the upload on its own tries and records its own `backup_failed`; the Owner gets one email per group (`BackupPostVideos::groupHasFailed()`). **Retry** (`POST app.posts.video-backup.retry`, Owner only, `RetryVideoBackup`) is refused (422 on `post`, `rxdesk.video_backup.errors.nothing_to_retry`) unless the post or its group has a `backup_failed` record; it clears the failed records of the post and its group and queues `ApplyVideoPolicy` at once, so the policy in force then decides: Keep stops (nothing is shown any more), Delete deletes, Backup uploads. `PostVideoRecords.vue` shows the "Backup failed" line and the Owner's Retry button.
- Videos are removed only through `SyncOwnedMedia` (which hands them to `DeleteOwnedMedia`), never by deleting files or rows directly, so `posts.media` and the thread replies stop listing them. Each removed video leaves a `video_records` row, shown in the post details by `PostVideoRecords.vue` (the card queries eager-load `videoRecords`).

### Cover (a video's uploaded image)

- A **Cover** image lives in the video item's meta, `media.*.meta.cover_image`: a whole media item (image row owned by the post), next to `cover_offset_ms`. It and a picked frame exclude each other: `SyncOwnedMedia` keeps the submitted image and drops the frame, and an item submitted without `cover_image` loses it. Never write `cover_image` anywhere else.
- It is owned media nested under its video (`SyncOwnedMedia::COVER_IMAGE`, synced like thread reply media): per-channel copies, the recurrence, the Quota and Disk guard (`MediaStorageObserver`) and the Video policy (removing the video releases its Cover image; Backup never uploads it) all work through the owned-media paths, with no Cover-specific code.
- Which posts take one: `ContentType::supportsCoverImage()` (today Instagram Reel, Instagram Feed, YouTube Short, Facebook Post and Facebook Reel; a Facebook post takes one only as a single video, never with an image or several media), and only on the single video of the post (`App\Support\Media\CoverImage::fitsPost()`). A later network adds its type there. The file rules (JPEG or PNG, at most `CoverImage::MAX_BYTES`, 8 MB) live in `CoverImage` too, read by the composer from the content type's media rules and listed by `list-content-types-tool` (`supports_cover_image`, `cover_image_max_bytes`, `cover_image_mime_types`). `PostCompositionValidator` refuses every violation on every save (web, API, MCP), keyed `media.{n}.meta.cover_image`; `PostMediaRules` only checks the shape. The composer strips the shared Cover image from a channel whose post cannot take it (`mediaForContentType()`, `lib/coverImage.ts`).
- Instagram: `InstagramPublisher::reelCoverParam()` sends `cover_url` instead of `thumb_offset` (an approved upstream change; carousels keep `thumb_offset`). A PNG goes through `CoverImageJpeg`, which writes a JPEG copy into `social-crops/` (pruned by `PruneTemporaryUploads`).
- **After-publish networks (YouTube and Facebook):** a network that takes the Cover only once its video is up never touches its publisher. `ScheduleCoverSetting` (listener on `PostStatusChanged`, like `ScheduleVideoPolicy`) queues `SetPostCover` `FIRST_DELAY_SECONDS` after a post moves into `published`, only when `NetworkCovers::for($platform)` has a setter and `CoverImage::forPost()` finds the Cover. The job calls the setter (`NetworkCover::set()`): `CoverNotReady` (still processing, 429, 5xx, no connection) is released on `BACKOFF_SECONDS` for 8 tries, about 30 minutes in all; `CoverRefused` (400, 403, 404, processing `failed`, a dead token) fails at once. Success records `set`, a refusal or the last try records `failed`, in `cover_outcomes` (`CoverOutcome`, one row per post: `outcome`, `attempts`, `last_error`, of which only `outcome` reaches the payload). The post stays published, nothing is emailed and there is no retry button. **A new network is one `NetworkCover` class, one entry in `NetworkCovers::SETTERS` and its type in `supportsCoverImage()`**; the job, the outcome, the `cover_outcome` post prop and the "Cover couldn't be set" line (`PostCoverOutcome.vue`, `rxdesk.cover.outcome.failed`) are shared. Instagram sends its Cover with the Reel and records no outcome.
- YouTube (`YouTubeCover`): reads `videos.list?part=processingDetails` (`data_api`, 1 unit) and only when `processingStatus` is `succeeded` posts the raw image to `thumbnails.set` (`upload_api`, `uploadType=media`, about 50 units; the upload host is `config('trypost.platforms.youtube.upload_api')`). The Thumbnail tab offers only the upload there (no frame picker).
- Facebook (`FacebookCover`, Page videos and Reels alike, checked on a real Page in November 2026 with the **current** connect scopes, so the Facebook connect is unchanged and no Page needs reconnecting): reads `GET /{video-id}?fields=status` (`config('trypost.platforms.facebook.graph_api')`) and only when `status.video_status` is `ready` posts the image to `POST /{video-id}/thumbnails` as multipart (`source`, `is_preferred=true`, `access_token`). `error` / `expired` refuse at once; a transient Graph failure (`GraphError::isTransientFailure()`: 5xx, 429, rate-limit codes, an unparseable body) or no connection tries again; any other Graph refusal, a dead token included, is final. The video id is `posts.platform_post_id`. `FacebookPublisher` is untouched; the Thumbnail tab offers only the upload there.
- The composer's Thumbnail tab (`MediaEditorThumbnailPanel.vue`) offers "Pick a frame" or "Upload an image" (uploaded through the chunked media upload); previews show the image as the video's poster.
- **MCP and the REST API** give the Cover as a reference in the item's meta, `meta.cover_image` = exactly one of `{upload_token}`, `{url}` or `{id}` (`PostMediaRules::metaRules(referenced: true)`, no nested rules: they would make `validated()` drop the item's other meta keys; the web keeps sending the whole hosted item). `HostInlineMedia::item()` resolves it into a hosted image item (a `url` is downloaded as a temporary upload, images only), on create, batch, update and both attach endpoints and tools, so every surface stores the same thing; the checks stay `CoverImage` on every save, and `AppendPostMedia` runs them on an attach (`media.{n}.meta.cover_image`). No tool of its own (annotations unchanged). Descriptions read `CoverImage::documentation()`; `list-content-types-tool` and the API listing carry `supports_cover_image`. `tests/Feature/Parity/CoverParityTest.php` proves the three surfaces agree.
- A post read (`PostResource`, web payload aside) shows the Cover in `media.*.meta.cover_image`; `cover_outcome` (`PostResource::coverOutcome()`, null for now, so the key is left out) is where the post-publish outcome of YouTube and Facebook joins.

### Invites (Owner guard)

- `AcceptInvite` is the one place an Invite moves a user into the inviting account, and it refuses (`Result::OwnerHasWorkspaces`, copy `rxdesk.invite.owner_has_workspaces`) a user who owns their account while it still has workspaces: moving them would lock them out of their own. They join as a Member with a different email. An Owner with no workspace left (the empty shell a signup through an Invite leaves) still accepts. Never move the guard out of `AcceptInvite`.

### Storage (Quota)

- `App\Services\Storage\AccountStorage` is the only code that computes storage: Storage used (media rows of the account's workspaces, minus logos; avatars have no workspace), the Quota (`accounts.quota_bytes`, null = `RXDESK_DEFAULT_QUOTA`), `canStore()` / `refusal()` and the refusal message (the Owner hears "your storage", anyone else "the workspace owner's"). A new reason to refuse is one more check in `refusal()` and one more `App\Enums\Storage\StorageRefusal` case. Never sum `medias.size` anywhere else.
- Enforcement: `MediaStorageObserver` refuses every new media row (upload, import, per-channel copy) with a `StorageRefused` validation error and deletes the file stored for it (`AccountStorage::ensureCanAdd()`: the Disk guard refuses every row, avatars and logos included; only the Quota exempts rows that do not count). The avatar and logo uploads also validate `DiskHasRoom` on `photo`, because they clear the old file before adding the new one: the refusal must come before the clear. `FitsStorage` refuses a chunked upload's declared size; `FitsStorage::forImport()` refuses a picker import whose declared size (the Drive Picker's `sizeBytes`, sent as `file.size`) does not fit, or of unknown size while the storage is full. `RemoteMediaImporter` asks `AccountStorage` again before any byte lands: a declared `RemoteFile::$size` that does not fit is refused before the request, and the stream is capped at `AccountStorage::room()`, so a Content-Length over it stops before the body. A queued import records `storage_full` / `owner_storage_full` instead (`ImportRemoteMedia`, `ExportCanvaDesign`, mapped in `useMediaImport.ts`). The refusal speaks to the signed-in user (`Auth::user()`, which the API and MCP guards set too).
- Publishing is never refused: `ScheduleNextOccurrence` copies media inside `AccountStorage::unguarded()`. Any other system path that must keep working over Quota goes through it too. Nothing is ever deleted for being over Quota.
- Disk guard: `refusal()` checks it first (`StorageRefusal::DiskGuard`, "the server is out of space", the same words for Owner and Member, a queued import records `server_out_of_space`), so every enforcement point covers it and `unguarded()` exempts publishing from it too. Free space comes from `App\Services\Storage\DiskSpace` (bound to `LocalDiskSpace`, the default filesystem disk's root); tests bind `Tests\Support\FakeDiskSpace::bind(free: ...)` (`tests/Pest.php` binds 500 GB for every test). The threshold is `RXDESK_DISK_GUARD_THRESHOLD` (10GB). The `rxdesk:quota` over-commit warning compares the Quotas with free disk + all Owners' Storage used - the threshold (`AccountStorage::usableSize()`).
- The System admin uses `$R php artisan rxdesk:quota show|set <email> [20GB|default]` and `$R php artisan rxdesk:usage`.
- The Owner's storage bar (account menu, `StorageBar.vue`, links to Preferences `#video-policy`) reads the shared `storage` prop (`HandleInertiaRequests::storage()`, a closure, null for anyone who is not an account Owner), which gets its numbers from `AccountStorage::usage()`.

### Production (`compose.rxdesk.yaml`)

Upstream's `compose.prod.yaml` and `Caddyfile` stay untouched (it pulls TryPost's image and publishes the app's ports); The RX Desk runs `compose.rxdesk.yaml` + `docker/Caddyfile.rxdesk`, so upstream merges never conflict. Settings come from `.env.production` (git-ignored), started from `docker/.env.production.example`. Every command takes `-f compose.rxdesk.yaml --env-file .env.production`; the project name is `therxdesk-prod`, so it never shares a container or volume with the dev stack.

- The image is built on the VPS (target `production`) with `VITE_APP_NAME`, `VITE_REVERB_HOST=<APP_DOMAIN>`, port 443, `https` and PostHog off. Vite bakes them in: rebuild after changing `APP_NAME`, `REVERB_APP_KEY` or `APP_DOMAIN`. The server reaches Reverb inside the container (`REVERB_HOST=127.0.0.1`).
- Only Caddy publishes host ports (80, 443). The app, Postgres and Redis publish none. `APP_URL` and every OAuth redirect URI are built from `APP_DOMAIN`.
- Caddy has a fixed address (`CADDY_IP`) on the `edge` network, whose subnet is fixed (`EDGE_SUBNET`, a private range); `TRUSTED_PROXIES` is that one address, so a request that skips Caddy cannot fake its IP. Change `CADDY_IP`, `EDGE_SUBNET`, `EDGE_DYNAMIC_RANGE` and `EDGE_GATEWAY` together.
- Set explicitly: `SELF_HOSTED=true`, `RXDESK_DEFAULT_QUOTA`, `RXDESK_DISK_GUARD_THRESHOLD`, the legal links; off: `POSTHOG_ENABLED`, `NIGHTWATCH_ENABLED`, `CHANGELOG_ENABLED`, `TELESCOPE_ENABLED`, `GOOGLE_AUTH_ENABLED`, `GITHUB_AUTH_ENABLED`, Google Photos and Canva. The composer's Drive picker (`GOOGLE_DRIVE_ENABLED`) defaults to off and can be turned on in `.env.production`; the Drive backup needs only `GOOGLE_MEDIA_CLIENT_ID` / `_SECRET`. No `STRIPE_*`.
- Horizon runs the `video-policy` supervisor (Drive backups, up to 3 hours per run) next to upstream's; see "Video policy" for the timeouts.
- `www.<APP_DOMAIN>` only redirects to the bare domain (Caddy gets a certificate for each). Cloudflare holds the DNS: both A records stay **DNS only** (grey cloud: Caddy issues its own certificates, the app must see the client's IP, and Cloudflare's free proxy caps uploads at 100 MB), and there is no AAAA record (Docker's IPv6 port forwarding would hide the client's IP).
- Mail goes out through Resend's SMTP (`smtp.resend.com`, user `resend`, the API key as password, `MAIL_SCHEME=smtp` on 587: Symfony accepts only `smtp` / `smtps`, never `tls`). Mail to `admin@<APP_DOMAIN>` is received by Cloudflare Email Routing (MX at the apex; Resend's records live on `send.` and `resend._domainkey`).
- Every service's log rotates (`x-logging`: 5 × 20 MB).
- The legal links point at the app's own `/privacy` and `/terms` (`LegalPageController`, routes `legal.privacy` / `legal.terms`, public). Their text is English Markdown in `resources/legal/*.md` (first line `# Title`, `{#id}` heading anchors), content rather than UI copy, so it is not in `rxdesk.php`. The privacy page carries what the platform reviews ask for (Google Limited Use, the YouTube/Google links, `#data-deletion` for Meta); `tests/Feature/RxDesk/LegalPagesTest.php` keeps them there. Update its "Last updated" line when the text changes.
- Secrets live only in `.env.production` (mode 600). `~/rxdesk-secret.sh NAME [NAME ...]` (outside the repo) writes one value into it (into each name given) without showing it.
- Every network that needs a developer app of ours (Facebook, Instagram, Instagram via Facebook, Threads, TikTok, YouTube, LinkedIn and LinkedIn Page, X, Pinterest, Google Business) is off in production until `.env.production` sets its `*_ENABLED=true` next to its credentials, so Channels never offers a connect that cannot work. Bluesky, Mastodon, Telegram and Discord need no app of ours and keep upstream's default (on).
- Google: one Cloud project and one OAuth web client serve YouTube (`GOOGLE_CLIENT_*`) and the Drive backup (`GOOGLE_MEDIA_CLIENT_*`, the same values), with the YouTube, Drive and picker callbacks registered on it. Its publishing status must be **In production** (Testing expires refresh tokens after 7 days). The YouTube scopes stay out of its Data Access list until the verification is filed (they need a justification and a demo video); until then users see Google's "unverified app" screen (Advanced → continue) and the app takes at most 100 new Google users. Uploads from an unverified project publish with the privacy the post asks for (checked November 2026 on a real upload and in the `videos.insert` docs: uploads cost 1 unit of a separate Video Uploads bucket, 100 a day).
- `docker/Caddyfile.rxdesk` answers 404 for `/stripe` and `/stripe/*` (Cashier's webhook accepts unsigned events without `STRIPE_WEBHOOK_SECRET`). A new env variable the app needs goes into the compose file's `environment:` and the example file together.
- Check without starting anything: `docker compose -f compose.rxdesk.yaml --env-file docker/.env.production.example config`.
- Live since November 17, 2026 at `therxdesk.com`. Deploy an update from `main`: `build app`, then `up -d` (the entrypoint migrates and caches). A changed `.env.production` value needs only `up -d`, unless it is baked into the build (see above). Admin commands run as `docker compose -f compose.rxdesk.yaml --env-file .env.production exec -T app php artisan ...` (`rxdesk:code`, `rxdesk:quota`, `rxdesk:usage`).
- Networks on at launch: YouTube, Facebook and Instagram through a Facebook Page (one Meta app, Business type, Live mode, no App Review: every member who connects Facebook or Instagram must hold the Tester role on it, at most 50 testers without a verified business). Instagram Login and TikTok were left for later; TikTok needs a public homepage (its review refuses a login page), domain verification for `PULL_FROM_URL`, App Review and then the Content Posting audit, and until the audit it posts private only, for at most 5 users a day.
